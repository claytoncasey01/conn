# Open work

`#/work` lists the open tickets of the Jira projects in Settings that are in the current sprint, not done, and yours or unassigned (a Jira `statusCategory` filter: no workflow's status names are spelled anywhere, and the page shows whatever status Jira returns). It is there only while the Atlassian module is on and lists at least one project key (Settings, Services): otherwise the nav item, the `#/work` pages ("Atlassian is off. Enable it in Settings."), the Open work API, ticket sessions and the ticket half of the History filter are gone, and conn makes no Atlassian call. A change in Settings takes effect at once. Pick a ticket and a research model (Haiku or Sonnet 5.5), then START. A run builds in the repository `atlassian.jira.buildRepo` (Settings), in its local clone found as for every repository (a folder in Settings, `<cloneRoot>/<repo>`, or `~/projects/<repo>`); with no clone START is disabled and says what to set. Nothing is cloned for you. A run starts from, and its PR goes into, the Base branch on the Atlassian card (`atlassian.jira.baseBranch`: a branch name, letters, digits and `. _ - /`, starting with a letter or digit, no `..`, at most 100 characters; the page checks it as the server does), or, when that is empty, the clone's default branch as its git config says (`refs/remotes/origin/HEAD`, which `git clone` sets; read from disk, no network). A clone that cannot say (made with `git init`) needs a Base branch, and START says so. The card sends it with its explicit Save (empty clears it); a `PUT /api/settings/atlassian` that leaves `baseBranch` out keeps it. conn never pushes to the base, the default branch, `main`, `master`, `develop`, `development`, `staging` or `hotfix`, and OPEN PR only pushes a branch named for the ticket's key.

1. Fetches, creates a worktree beside the clone, named `<clone folder>-<ticket key lowercase>`, on the branch `<ticket key lowercase>-<slug>`, and moves a to-do ticket into an in-progress status (the one status of Jira's In Progress category its workflow offers; with none or several it moves nothing and says so).
2. Four read-only research agents (Jira, Confluence, Slack, code) report; a Sonnet pass writes a brief, what the sources already answered, and up to five questions only you can settle.
3. You answer in the UI. The brief goes to `<worktree>/.conn/brief.md` and a cmux workspace named after the ticket starts `claude` on it. If cmux fails, the page shows the command to paste.
4. OPEN PR (after a confirm) pushes the feature branch, opens the PR (a `gh` call, so the GitHub module must be on) and moves the ticket to its review status, when the workflow has exactly one status whose name says review; otherwise it moves nothing.

The build session runs on Sonnet with a delegation rule (`.conn/delegation.md`, appended to its system prompt): repo maps, call-site greps and API lookups go to the read-only Haiku agents `search`, `grep` and `docs`, each spawned with a specific description so they are labelled in the agent tree. The agent definitions are in `agents/`; copy them to `~/.claude/agents/` (`cp agents/*.md ~/.claude/agents/`) if they are not there yet.

While a PR is open the run page polls GitHub (by URL, every 30 to 60 s) and shows checks, review and merge state. A red PR offers `FIX FAILING CHECKS`, which types a short instruction naming the failed checks into the build session, with the commands to read them that name the PR's repository (`gh pr checks <n> -R <owner/repo>`, so a fork's gh default cannot point them at the upstream; CI log text is never pasted in). It is refused while the GitHub module is off or the PR's repository is off the list (the status shown may then be old). After a merge you can `MOVE JIRA TO` a status you type and `REMOVE WORKTREE`, which refuses while the session runs or files are uncommitted and never forces, and removes only the worktree path the run recorded when git itself lists it as a linked worktree (never the clone, never a folder git does not know). A run whose session exited can `RESUME SESSION` on the same conversation. With `CONN_WORK_DRY=1` the PR walks through pending, red (odd tickets) or green, approved, merged; OPEN PR and that walk need the GitHub module on, and a seeded `CONN_WORK_DRY` run starts with it off (turning it on there is safe: every module stays dry in a seeded run).

Everything outside git goes through headless `claude -p` runs, so Jira, Confluence and Slack use your claude.ai connectors; the Slack reader runs only while the Slack module is on. Helper runs are named `conn:*` and hidden from Sessions. Runs persist in `~/.conn/runs`.

What Open work writes, and all of it: `$CONN_DATA/runs/<KEY>.json` (one per run), `work-cache.json` (the last sprint list) and `jira-site.json` (the Atlassian site id and your account id); in the clone, a git worktree and branch beside it, and `<worktree>/.conn/` (the brief, the delegation rule, the PR body; excluded from git); `git fetch origin` in the clone, `git push -u origin <branch>` and `gh pr create --repo <the run's repository>` (named, never left to gh) when you press OPEN PR; and in Jira, only the status moves above (to an in-progress status at the start, to a review status when the PR opens, and to the status you type after a merge). What it calls: Jira, Confluence and (with Slack on) Slack reads through the connectors, `gh pr view <PR url>` while a PR is open (only while the GitHub module is on and the PR's repository is allowed), and `git`. Text from Jira (titles, descriptions, comments) is data: it is shown as text, never as HTML, and a ticket key is checked against the pattern built from your project keys before it reaches a path, a branch name or a prompt.

Env: `CONN_DATA` (default `~/.conn`), `CONN_CLAUDE` (claude binary), `CONN_CMUX` (cmux binary), `CONN_PORT`, and `CONN_WORK_DRY=1` to fake tickets and the whole pipeline with no git, Jira or Claude. A dry server with no `settings.json` starts from the dry seed, with Open work on (see [Dry runs in Settings](settings.md)). `CONN_JIRA_PROJECT` and `CONN_REPO` are no longer read: the build repository and the project keys are settings.
