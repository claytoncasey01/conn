# Open work

`#/work` lists the open tickets of the Jira projects in Settings that are in the current sprint, not done, and yours or unassigned (a Jira `statusCategory` filter: no workflow's status names are spelled anywhere, and the page shows whatever status Jira returns). It is there only while the Atlassian module is on and lists at least one project key (Settings, Services): otherwise the nav item, the `#/work` pages ("Atlassian is off. Enable it in Settings."), the Open work API, ticket sessions and the ticket half of the History filter are gone, and conn makes no Atlassian call. A change in Settings takes effect at once. The repositories are chosen per ticket, at START, never in Settings: pick a ticket, the repositories to build in, a research model (Haiku or Sonnet 5.5) and, if you like, the build advisor (As in Settings, the default, leaves it to the Advisor model in Settings when the build session starts), then START. The start panel lists every allowed repository conn knows of: those Settings names (the Default repository, an exact allowlist entry, a clone folder set in Settings, or a repository with a base branch of its own) and those found on this machine (a clone directly in the clone folder or in `~/projects`, named for its repository as conn looks for it, then the repositories of live sessions and My PRs rows). A pattern such as `acme/*` names none by itself. They are in allowlist order, and in the order found within a pattern, at most 200, each with the branch a run starts from there. A repository a run cannot start in (no local clone, found as for every repository: a folder in Settings, `<cloneRoot>/<repo>`, or `~/projects/<repo>`; or no branch to start from) cannot be ticked and says what to set. Nothing is cloned for you. Tick one or more, at most 6; the first ticked is the lead. With two or more a choice appears: one session across them, or one session per repository (`atlassian.jira.sessionLayout` is the one it starts on). START stays off, saying "Choose a repository", until one is ticked. The page remembers the choice and the layout in this browser (`localStorage`, `conn.work.repos` and `conn.work.layout`; it works without it) and starts on the remembered repositories that are still ready, else on the Default repository (`atlassian.jira.buildRepo`, optional: with none set, nothing is ticked), else on none. `POST /api/work/<KEY>/start` takes `{ model, force?, repos?, layout?, advisor? }`: `advisor` is `claude-code`, `fable`, `opus` or `sonnet` (anything else is a 400), kept with the run for its build sessions; `repos` is the list of names in order (absent or empty: the Default repository, refused with "Choose at least one repository." when there is none, so a client that sends no `repos` gets today's one-repository start), `layout` is `shared` or `split`. A `repos` that is not a list of names, or another layout, is a 400; a repository chosen twice (in any case), two that are the same clone folder, one not allowed, one not ready or more than 6 are refused together, one sentence each, in one 409. Each repository starts from, and its PR goes into, its own base branch on the Atlassian card (`atlassian.jira.baseBranches`), else the Base branch for every repository (`atlassian.jira.baseBranch`: a branch name, letters, digits and `. _ - /`, starting with a letter or digit, no `..`, at most 100 characters; the page checks it as the server does), or, when both are empty, the clone's default branch as its git config says (`refs/remotes/origin/HEAD`, which `git clone` sets; read from disk, no network). A clone that cannot say (made with `git init`) needs a base branch, and the panel says so. The card sends it with its explicit Save (empty clears it); a `PUT /api/settings/atlassian` that leaves `baseBranch` out keeps it. conn never pushes to the base, the default branch, `main`, `master`, `develop`, `development`, `staging` or `hotfix`, and OPEN PR only pushes a branch named for the ticket's key. A run that is working (starting, researching, asking or building) or has a PR open cannot be started again; one that is cancelled, failed or interrupted can, and the new run replaces it. A repository the two runs share reuses its worktree when it is on the run's branch, and is refused while its branch was cut from another base than runs start from there now (one sentence per such repository, naming it when either run has more than one). A worktree of the old run in a repository the new one leaves out stays on disk as it was, and the new run's first log line names it: conn removes nothing for you. A run's repositories are fixed once it has started: to add or drop one, cancel the run and start the ticket again.

1. For each chosen repository in order, runs `git fetch origin <base>` in its clone and creates a worktree beside it, named `<clone folder>-<ticket key lowercase>`, on the branch `<ticket key lowercase>-<slug>` (the same name in every repository); a failure names the repository, and Retry keeps the worktrees already made and goes on from the one that failed. Then, once every worktree is ready, it moves a to-do ticket into an in-progress status (the one status of Jira's In Progress category its workflow offers; with none or several it moves nothing and says so), so a ticket never reads In Progress for a run with no worktrees.
2. One research stage for the run: four read-only research agents (Jira, Confluence, Slack, code) report; a Sonnet pass writes a brief, what the sources already answered, and up to five questions only you can settle. With several repositories every reader's prompt names each repository and its worktree, and the code reader may read all of them (its folder is the lead's worktree, the others are added to it).
3. You answer in the UI. One brief goes to `<worktree>/.conn/brief.md`: in the lead's worktree in the shared layout, in every worktree in the split one. With several repositories the shared brief lists one line per repository (repository, worktree, branch, the branch its PR targets), tells the session to work only in those directories, each on its own branch, and to write `.conn/pr-body.md` in each worktree with changes; a split brief names its own repository, lists the others as ones the run also builds in and another session works in, and says to ask you before changing anything outside its own. A one-repository brief reads as it always did. Sessions open where Settings say (inside Conn, a cmux workspace, or a command to paste), named after the ticket, each running `claude` on its brief. Shared: one session in the lead's worktree, with each other worktree added with `--add-dir`. Split: one session per repository, each in its own worktree. Writing the brief also removes any `.conn/pr-body.md` or `.conn/replies.json` the repository left there; at OPEN PR the body is read from `.conn/pr-body.md` only as a regular file in a `.conn` folder of yours (a link is refused) and is handed to `gh` on its standard input (`--body-file -`), never as a path or an argument. A body larger than 64 KiB, holding a NUL byte or not UTF-8 is refused with every reason at once; with no `.conn/pr-body.md`, the body made from the commit subjects is cut to fit 64 KiB. Only a repository with a session of its own has a session, a Claude session id and a command to paste: in the shared layout that is the lead only. If the session does not start, the page shows the command to paste, on that session's repository. In the split layout a repository that may not build when its session is due (it left the allowlist, or has no clone any more) gets no session and no files, the log says so, and the other sessions open.
4. OPEN PR (after a confirm) pushes each repository's feature branch, opens its PR (a `gh` call, so the GitHub module must be on) and moves the ticket to its review status as the review-move setting says, when the workflow has exactly one status whose name says review; otherwise it moves nothing. Every repository with commits gets its own PR into its own base branch, with the same branch name and title; a repository with no commits is skipped and the log says so.

The build session runs on Sonnet with a delegation rule (`.conn/delegation.md`, appended to its system prompt; RESUME SESSION, and a resume at launch, append it only while it is a regular file in a `.conn` folder of yours, reached through no link, holding exactly the text Conn wrote; otherwise the session resumes without it): repo maps, call-site greps and API lookups go to the read-only Haiku agents `search`, `grep` and `docs`, each spawned with a specific description so they are labelled in the agent tree. The agent definitions are in `agents/`; conn links them from `~/.claude/agents/` itself when the server starts (see [Agents and skills](settings.md#agents-and-skills)), so there is nothing to copy. If you copied them by hand earlier, those files are yours and conn leaves them: delete them and conn links its own at the next start.

**Sessions inside Conn.** With sessions opening inside Conn (the default), each build session's terminal is on the run page and on Sessions. RESUME SESSION reopens a repository's session there, as `claude --resume <id>` when the run holds Claude's session id, else with `--continue`. A build session that still ran when Conn quit is resumed at the next launch, on its own conversation, only while its run is building or has a PR open and nothing else is changing it, its worktree still exists, its repository is still allowed and cloned, no session works there already, and the run holds Claude's session id (a run without one is not resumed at launch; RESUME SESSION keeps its `--continue`). In a dry run (`CONN_WORK_DRY=1`) the session is a scripted stand-in drawn inside Conn, which echoes what you type and sends nothing; it is never resumed at launch. With sessions set to open in a terminal or as a command, a dry run opens nothing.

**Pull requests, one per repository.** The run page shows one row per repository when a run has more than one, each with its branch and base, commits and changed files, PR with checks and review, and the buttons that apply to it: OPEN PR, FIX FAILING CHECKS, RESUME SESSION and REMOVE WORKTREE. OPEN ALL PRS, in the footer, appears while more than one repository has commits and no PR. A one-repository run looks as it did. OPEN PR works while the run is `building`, and while it is `pr_open` and some repository with commits has no PR. Pressed for one repository it opens that one (`{ "repo": "acme/api" }`); pressed for all, it opens every repository that has commits and no PR, one after another, each pushed with its own `git push -u origin <branch>` and opened with its own `gh pr create --repo <that repository>`, so a fork's gh default cannot send it elsewhere. Each repository is checked on its own, and one that is refused does not stop the others (the refusal is logged, naming it): its branch must be a plain name, not the base, the default branch or a protected name, and start with the ticket's key; its repository must still be allowed, with a clone still found in Settings (a repository whose clone is gone is refused, naming it); its worktree's git `origin` must be that repository (one that pushes elsewhere is refused, naming both); and the GitHub module must be on. These checks run again right before each push, because the settings can change while an earlier repository is being pushed. A failure in one repository (a push, a `gh` error) leaves the PRs that already opened in place and is reported with its repository; press OPEN PR again and only the repositories without a PR are tried. The run is `pr_open` once any repository has a PR.

**When the ticket moves to review** is the Atlassian card's "Move the ticket to review" (`atlassian.jira.reviewMove`): `first` moves it when the first PR opens; `all` (the default) moves it once every repository that has commits has a PR; `never` never moves it, and you move it yourself with MOVE JIRA TO. The move is the one above (a status of Jira's review category named so, exactly one match) and happens once per run: a move that fails (Jira unreachable, Atlassian off) does not count, and each later PR that opens tries again until Jira has answered (moved, already there, or no single review status). Commits that appear after the move do not take the ticket out of review. A one-repository run moves when its PR opens, under any of the three.

While a PR is open the run page polls GitHub (by URL, every 30 to 60 s) and shows checks, review and merge state. Each repository's PR is polled on its own schedule, with its errors logged once, keyed by ticket and repository; with several repositories the log lines name the repository. A red PR offers `FIX FAILING CHECKS`, which types a short instruction naming the failed checks into the build session that works in that repository (its own session in the split layout, the lead's in the shared one), with the commands to read them that name the PR's repository (`gh pr checks <n> -R <owner/repo>`, so a fork's gh default cannot point them at the upstream; CI log text is never pasted in). Pressed for all, it types one instruction per repository whose checks are failing; pressed for one, it refuses a repository whose checks are not failing. It is refused while the GitHub module is off or that PR's repository is off the list (the status shown may then be old). Alerts (`ALERTS` on Sessions) follow each repository's PR on its own: checks failed or passed, merged, closed, each titled with the repository when a run has more than one. There is no alert for a review that asks for changes.

After a merge you can `MOVE JIRA TO` a status you type. The run counts as merged when every PR it has is settled (merged or closed) and at least one merged; a repository with commits and no PR does not hold it back, and the page says so in that repository's row, where OPEN PR is still offered. `REMOVE WORKTREE` works on one repository at a time (pressed for all, on every repository whose PR merged or closed and that is not cleaned yet). It refuses while a session in that worktree runs or files are uncommitted, never forces, refuses a repository that has left the allowlist, naming it, and removes only the worktree path the run recorded when git itself lists it as a linked worktree (never the clone, never a folder git does not know). In the shared layout the lead's worktree is where the one session works and reaches the other worktrees from, so it is kept while another repository's PR is open (a PR not yet read counts as open) and, pressed for all, it is removed last; another repository's worktree is also kept while the lead's session runs, because that session reaches it. `RESUME SESSION` reopens the build session on the same conversation, once per session slot: the lead's in the shared layout, each repository's in the split one (pressed for all, every session that is not live; one that needs nothing is passed over, and a gap of 30 s per session stops a double press). A split session that was never launched (its repository was refused when the run opened sessions) is started fresh from its brief instead; the run page offers RESUME SESSION for it only once a PR is open, though the route accepts it sooner. With `CONN_WORK_DRY=1` each PR walks through pending, red (odd tickets) or green, approved, merged, each later repository's PR numbered 100 on from the one before; OPEN PR and that walk need the GitHub module on, and a seeded `CONN_WORK_DRY` run starts with it off (turning it on there is safe: every module stays dry in a seeded run).

Limits: at most 6 repositories in a run (`maxLegs`), 200 repositories offered in the picker, git read in at most 3 repositories of a run at a time (every 5 s), and a start panel's clone-folder listing reads at most 500 folders.

Everything outside git goes through headless `claude -p` runs, so Jira, Confluence and Slack use your claude.ai connectors; the Slack reader runs only while the Slack module is on. Helper runs are named `conn:*` and hidden from Sessions. Runs persist in `~/.config/conn/runs`.

What Open work writes, and all of it: `$CONN_DATA/runs/<KEY>.json` (one per run: the ticket's facts, the layout, and `repos`, one entry per repository holding its clone, base, branch, worktree, session and PR), `work-cache.json` (the last sprint list) and `jira-site.json` (the Atlassian site id and your account id); in each repository's clone, a git worktree and branch beside it, and `<worktree>/.conn/` (the brief, the delegation rule, the PR body; excluded from git; the brief only in the worktrees that have a session of their own); `git fetch origin <base>` in each clone, and, when you press OPEN PR, one `git push -u origin <branch>` and one `gh pr create --repo <that repository>` (named, never left to gh) per repository; and in Jira, only the status moves above (to an in-progress status at the start, to a review status when the PR opens, and to the status you type after a merge). What it calls: Jira, Confluence and (with Slack on) Slack reads through the connectors, `gh pr view <PR url>` for each open PR (only while the GitHub module is on and that PR's repository is allowed), and `git`. Text from Jira (titles, descriptions, comments) is data: it is shown as text, never as HTML, and a ticket key is checked against the pattern built from your project keys before it reaches a path, a branch name or a prompt. A run file from before repositories were chosen per ticket (no `repos`) is read as a run in one repository and rewritten in the new shape the next time it is saved. A run file written by this version is not readable by the previous one, which would read it as a run with no branch, worktree or PR: do not go back to an earlier conn while a run is in flight.

Env: `CONN_DATA` (default `~/.config/conn`), `CONN_CLAUDE` (claude binary), `CONN_CMUX` (cmux binary, for sessions set to open in your terminal), `CONN_PORT`, and `CONN_WORK_DRY=1` to fake tickets and the whole pipeline with no git, Jira or Claude. A dry server with no `settings.json` starts from the dry seed, with Open work on (see [Dry runs in Settings](settings.md)). `CONN_JIRA_PROJECT` and `CONN_REPO` are no longer read: the repositories are chosen at START, and the default repository and the project keys are settings.
