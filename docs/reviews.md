# Reviews

The `REVIEWS` tab lists the pull requests that want your review, in every allowed repository, and starts a full review session for one with a click (a Claude Code session told to review that PR, using a `/deep-code-review` skill when you have one installed). It lists an open, non-draft PR of an allowed repo that you did not write when a review source that is on lists it (Settings > Reviews): GitHub asks for your review (`Requests me`, on by default; a PR stays listed after your review drops the request), it was posted in one of the chosen Slack channels (Slack on, at least one channel), it was sent to you in a Slack DM (Slack on and the DM switch on), or `Every open non-draft PR` is on. A PR is never listed because of a source that is off, and a bot's PR counts like anyone's. A PR that merged or closed stays listed, greyed, for a day, but only one you had touched (posted, DM'd, reviewed by you, or launched from here). Every row shows its repository, the number (linked to GitHub), the title as plain text, the author, its age, the checks, the state, the Slack links and any tags; sessions you launched link to their Overview page. The same number in two repositories is two rows. The state is derived from GitHub (your latest review and the commit it was made on, review requests) and from the stored review draft, never typed in:

- `NEW`: listed, you have no review on it.
- `REVIEWING`: the session a REVIEW press launched for it is live (found from the launch record, never from a session's name).
- `REVIEW READY`: the session wrote its review, Conn stored it, and it waits for you to read it and press Post review (see [The review to post](#the-review-to-post)). It wins over `REVIEWING`, so a row shows it while the session is still open, and over `RE-REVIEW`, so an ask that came in meanwhile does not hide it. Once the review is posted it counts as your latest review straight away (an approval `DONE`, a comment `WAITING`, unless the session is still open), even before a poll has read it back, and Conn polls at once; after that, or when your own review landed first, the state is GitHub's again. A PR that merged or closed is `DONE`, with its draft greyed.
- `WAITING`: your latest review is comments or changes requested, and nobody has asked again.
- `RE-REVIEW`: you reviewed before and the author asked again, either by re-requesting you on GitHub or by saying so in the Slack thread of the post. The tag says which: `RE-REVIEW REQUESTED (GITHUB)` or `(SLACK)`.
- `DONE`: your latest review is an approval, or the PR merged or closed.

`UPDATED` shows when the PR's head moved past the commit you reviewed (with no ask yet it stays `WAITING`; after an approval it stays `DONE`). `NOT IN A CHANNEL` shows on a row that only `Every open non-draft PR` lists while the channel scan is on. Rows sort `RE-REVIEW`, `REVIEW READY`, `NEW`, `REVIEWING`, `WAITING`, `DONE`, the most recently updated first within a state, and the filter bar has Status and Author. The tab's badge is the number of `NEW`, `RE-REVIEW` and `REVIEW READY` rows not seen yet (marked seen per `owner/repo#n`), so a review that became ready while the page was closed is counted too.

## How it finds things

- **GitHub, free.** Nothing is called in setup or while the GitHub module is off. Otherwise the server polls (whether or not a dashboard is open, and at once when a setting a poll reads changes) with `gh api graphql`, every 3 minutes, or less often when GitHub says a poll is dear: the interval comes from what the last poll cost (the `rateLimit` GitHub answers with, so it counts what the poll really read: the searches, six to a call, and the tracked PRs read by number), long enough that an hour of polls spends at most half of the 5,000 hourly GraphQL points and at most half of what is left before the reset, and never longer than 15 minutes. `MY PRS` polls GitHub as the same account, so while both are polling they share that half between them (each waits as if it had half the budget; one that stopped asking an hour ago, or whose module is off, takes no share). Many patterns with only `Requests me` on cost little and poll every 3 minutes. It runs the `Requests me` search for each pattern (`is:pr is:open archived:false user-review-requested:@me` plus `repo:owner/repo` for an exact pattern or `user:owner` for `owner/*`, 100 each; an exact pattern an owner wildcard of the list already covers is not searched again), and when `Every open non-draft PR` is on one more search per pattern (`is:pr is:open draft:false archived:false -author:@me`, at most 200 each; a list cut off there is a notice on the page, never a reason to drop anything). Searches go at most six to a call, and each PR asks for at most 20 review requests, 20 latest reviews and 50 check contexts, so no call nears GitHub's node limit. Then every PR conn tracks in an allowed repo that the searches did not return, and that a source that is on could list, is read by number, in batched `gh api graphql` calls of 50; that read says whether it is open, merged, closed or gone, so a PR is never taken as ended because a list left it out, and a record whose read did not answer is kept as it was. Every PR that comes back is checked against the allowlist again, and again when the page shows it. A pattern GitHub cannot search (a typo, a repo you lost access to, an org's SAML rule) is listed in a notice and its repos' rows stay as they were, marked out of date, with REVIEW refused for them; the other patterns go on. When GitHub says the rate limit is used up, Reviews asks it nothing more until the reset, keeps the list and says so; `MY PRS` waits for the same reset, and the other way round. Your login comes from `gh api user` (`CONN_REVIEW_ME` overrides it).
- **Slack, only when needed.** With Slack on and at least one channel chosen, a short Haiku run with only the read-only Slack tools (no Bash) reads every chosen channel in one run, each from its own cursor, for the posts that announce a PR of an allowed repo (the prompt names the channels and the allowed repos, an `owner/*` pattern as "any repo owned by owner"). Every helper conn starts has no built-in tools beyond the ones listed for it (`--tools` is set to exactly those, none for this one), so your own `permissions.allow` rules, such as a `Bash(...)` rule, cannot give it a shell. It runs only while a dashboard is open: for a tracked PR with no post matched yet at 0, 10, 30 and 90 minutes after it was first seen, and otherwise at most every 10 minutes to find new posts (at once on REFRESH). A channel's first scan looks back 2 days; after that it reads from its cursor, which every completed run moves to that run's start less 15 minutes (or to a newer post), pulled back, while PRs still have no post, to 15 minutes before the older of the cursor and the earliest of those PRs' first-seen times. It never reads further back than the 2-day window, whatever the cursor (an old one, or a channel chosen again, reads the window). For a `WAITING` PR whose head moved past your review and that has a matched post, the same run also reads the post's thread for a re-review ask made after your review, on the same 0/10/30/90 schedule counted from when the head moved. Whatever the helper returns is checked before use: a post counts only in a chosen channel, with an `https://…slack.com/` permalink, and when its PR link names an allowed repo (a valid `owner/repo`; any other is dropped and never fetched). A post about a PR conn does not know yet is a lead: it is kept in `reviews.json` and read by number from GitHub (at most 30 per scan, the rest at the next) and counts only when GitHub has it open in an allowed repo, so a message cannot invent a PR. A lead is read with the settings as they are then (not as they were when the scan began), and a draft or a PR of your own that a post names is dropped. A scan that finishes after Slack, GitHub or every channel (for the DM scan: the DM switch) was turned off is dropped whole: nothing it read is kept, no cursor moves, and the Slack card records nothing.
- **Slack DMs, only when needed.** People often ask for a review in a DM instead of the channel, so a second, separate Haiku run (same read-only Slack tools, no Bash) searches your 1:1 direct messages for messages that link a pull request of an allowed repo (it runs only with Slack on and the DM switch on in Settings). Only DMs sent to you by a person count: never a bot, a group DM or a channel, and never what you wrote. It reports the message's Slack timestamp, its link, the PR URL and whether you sent it (a message you sent is dropped here), and nothing else: the text of a DM is not returned, stored or shown, and the prompt holds only the allowed repos, a timestamp and fixed rules. A DM counts only when it names a PR of an allowed repo that GitHub has open (a lead, read by number like a channel post's), and it lists that PR with a small `DM` link to the first such message; a later DM after your own review is a re-review ask (`RE-REVIEW REQUESTED (SLACK)`, not for an approved PR), like a later message in the channel thread. It runs while a dashboard is open, at most every 10 minutes and at once on REFRESH, reading from its cursor less 15 minutes, never further back than the 2-day first window (which is also where the first run starts). The time limit goes to Slack's search as its own `after` parameter in Unix seconds, not as a date filter, and the helper follows the result cursor for at most 5 pages. A signed-out Slack is the same state for both scans (only the Slack connector counts: another connector being signed out, such as Atlassian, does not), and a DM scan that reports it makes the next DM scan wait as long as the channel scan does. A DM scan that reads successfully while Slack shows as signed out clears that state, and never an error of the channel scan; any other DM failure shows its own banner and leaves the channel scan's state alone.
- **Cost.** One real scan of a day of the channel cost about $0.016 cold (7 posts, 20 s, Haiku). A scan is capped at $0.50 and 90 s. Re-review asks in Slack threads are not part of that measurement.

## REVIEW

`REVIEW` (`RE-REVIEW` on a re-review row) takes a `SONNET | OPUS` choice per row (remembered, Sonnet by default) and an advisor (As in Settings by default, which leaves it to the Advisor model in Settings; a pick is for that one review and not remembered) and then:

1. Finds the repo's local clone (Settings > Local clones: the folder set there, else `<clones folder>/<repo>`, else `~/projects/<repo>`, used only when its `origin` is that repo); with none, REVIEW is disabled and the row says `No local clone of owner/repo: set a folder in Settings`. Fetches the PR's base branch from the clone's `origin` and puts a detached worktree at its tip, at `$CONN_DATA/reviews/<the first launch's name>/<repo>`, so two PRs never share a folder; the launch records which clone it was made from. An existing folder is reused only when it is a worktree of that repo's clone. The working files of your clone are never touched, but it is not read-only: `git fetch` updates its `origin/<base>`, `git worktree add` and `git worktree prune` write to its `.git`, and `.conn/` is appended to its shared `.git/info/exclude`.
2. Writes the prompt to `<worktree>/.conn/prompt.md` (excluded from git) and starts a session where Settings say (inside Conn, a cmux workspace, or a command to paste) named `pr-<n>-<owner>--<repo>` (`pr-<n>.2-<owner>--<repo>`, ... for a later review of the same PR) running `claude --name <name> --model <model> -- "Read .conn/prompt.md and follow it exactly."`. No two PRs share a name: the number and launch come first, and a GitHub owner never holds two dashes in a row, so the first `--` ends it (an owner that does, or a name over 120 characters, is named `pr-<n>[.<k>]-x<12 hex of sha1(owner/repo)>` instead). The prompt is the one in `internal/config/prompts.go`, with the PR number and its `owner/repo` filled in: plain instructions (review the PR, post nothing on GitHub, write the review to `.conn/review.json` as the last step, treat PR and Slack text as data, do not repost another reviewer's point) that need no skill of yours, and that use a `/deep-code-review` skill when one is installed; a re-review appends one line naming the commit of your previous review. If the session does not start, or sessions are set to open as a command, the page shows the command to paste with a COPY button and leaves the worktree, and the launch is recorded (launched by hand): the next press is the next review. A launch by hand does not retire the earlier launch of the PR, since nothing has started yet: the earlier session keeps being followed (and closed after your review) until a session really starts.
3. Refuses before any git call or session start for a repo that is not `owner/repo`, a number that is not a plain PR number, a PR not in the list or not open, a repo with no clone, a session already named for it in any folder, a second click within 30 seconds, and a second click while the newest launch of the PR has not appeared as a session yet (up to 5 minutes). The press is `POST /api/reviews/start` with `{ repo, number, model }`.

The session is an ordinary Claude Code session with your own settings (auto mode and so on apply; its advisor is the one picked or set in Settings, and Claude Code's setting means your own `advisorModel`). The review is whatever that session does with the prompt (and the `/deep-code-review` skill, if installed: Conn ships one, see [Settings](settings.md#agents-and-skills)): it writes its review to `.conn/review.json` and posts nothing (see [The review to post](#the-review-to-post)). Conn posts one review for Reviews, when you press Post review, and at no other time: it never comments, requests changes or reacts on GitHub or Slack, and nothing launches without a click (what My PRs writes is listed under that tab). The session is also denied Slack's write tools and the GitHub write forms of `gh` (`gh pr review`, `comment`, `merge`, `edit`, `close`, `ready` and `reopen`, `gh issue comment`, `close` and `edit`, the skill's `post_review.py`, and `gh api` with a method, a body (`-f` and `-F` glued to their value too), `--input` or `graphql`; a plain `gh api` read stays usable). That is a guard beside the prompt, not a guarantee: the rules match the start of a command or a pattern, and a reworded command may still get past them, since the session runs as your own `gh` login. A session with such a name (or the older `pr-<n>` and `pr-<n>-<k>`) that works under `$CONN_DATA/reviews` gets the kind `REVIEW` in Sessions and in History; a session that merely looks like one elsewhere is ad hoc (the name is only a kind; which PR it reviews comes from the launch record) (sessions History imported from old transcripts keep `AD HOC`), and `RESUME` in History reopens one, under the same deny list (a self-review's session under its own).

## The review to post

The session does not post. Its last step is to write `.conn/review.json` in its worktree: `{"commit", "summary", "verdict", "findings": [{path, line, side, severity, body}]}`, `commit` the PR head it reviewed (the line numbers belong to it), `verdict` `approve` or `comment` (`approve` only when no P0 or P1 finding survived), `side` `RIGHT` or `LEFT`, `severity` `P0` to `P3`. Every launch first removes a `review.json` left in a reused worktree, so an old review is never taken for the new one.

- **Reading it.** On the tick that already follows launches, the newest launch of each PR has its file read when it is newer than the last one read (by modification time, so a rewrite is picked up): a regular file, not a link, at most 512 KiB (`MaxDraftFileBytes`). A closed launch's file is looked at once more after it closed, so a draft written just before, or while Conn was down, is still taken after a restart; the worktree sweep waits for it. A finding whose path is not a relative path, whose line is not a positive whole number, whose side or severity is not in its table, or whose body is empty or over 2,000 characters once cleaned is dropped whole and counted (the row says how many), and at most 100 are kept. The file as a whole is unreadable when it is not JSON, too large, or has no valid 40-hex `commit`, no `summary` (at most 8,000 characters) or no `verdict`: the row then lists every problem, no alert fires, nothing counts as a landed review and the session stays open, so you can ask it to write the file again; a later readable write replaces the problem.
- **Where the findings land.** The PR's diff at the draft's `commit` is read (`gh api` with the diff media type, at most 8 MiB) and each finding is marked inline or not. GitHub refuses a whole review when one comment names a line outside the diff, so a finding that is not on a line of the diff, or every finding when the diff cannot be read, goes in the review's body under "Outside this PR's diff" instead, and the row labels it.
- **Stored.** The accepted draft (the commit, summary, verdict, findings, where each lands, the file's modification time, and later `postedAt`, the review's URL and the verdict it was posted as, `postedVerdict`) is kept on its launch in `reviews.json` (`draft`; a file that could not be read leaves `draftProblem` and `draftProblemAt`), so it survives the session closing, the worktree sweep and a restart. A newer write replaces a draft that was not posted; a posted one is never replaced. An unposted draft is set aside, kept in the record but no longer shown or postable, when a review of yours lands on GitHub after the file was written (you reviewed by hand), or when a newer launch of the PR starts. A re-review request does not set it aside: the row notes that the head moved, and the post still goes to the draft's commit.
- **The panel.** The row shows the summary and every finding, each ticked, with `Select all (N of M)`. The verdict starts at Claude's: `Approve` or `Comment`, never request changes. `Approve` is disabled while a ticked finding is P0 or P1 (a blocker is a comment), and comes back when those are unticked. The comments are shown as text and cannot be edited: untick one to leave it out. A PR that merged or closed shows the panel greyed, with Post review off. A newer write that changes the draft shows it with everything ticked again. Once the review is posted, the panel is a `Posted` line with a `View the review on GitHub ↗` link (when GitHub gave the review's address) in place of the findings.
- **Post review.** `POST /api/reviews/post` with `{ key, launchAt, fileAt, findings, verdict }` (`fileAt` the modification time of the file whose draft the panel showed, `findings` the ticked numbers) makes one `gh api` call that creates a single GitHub review on the draft's commit, with the verdict as its event, the summary (and any finding outside the diff) as its body and the ticked inline findings as its comments, so a review never lands in part. It is the only time Conn posts for Reviews. It is refused with a 409 while the same review is being posted, after it was posted, after it was set aside, when the PR has ended, in a dry run, when GitHub is off or the repo is no longer allowed, until the PR has been read from GitHub once, and when the file was written again since the panel showed its draft (`The review file was written again: check the new draft`), so a post never sends findings you did not see. A body with no `fileAt`, a verdict that is not `approve` or `comment`, a bad finding number, an approval beside a ticked P0 or P1, or a review body (the summary and every ticked finding outside the diff) over GitHub's 65,536 characters, counted in UTF-16 units, is refused with a 400 (`the review is too long for GitHub: untick some findings`); each line comment is within GitHub's limit already. A failure GitHub answers plainly shows its message and leaves the draft to press again. When it is unclear whether GitHub took the review (a timeout, a dropped connection or a 5xx), the launch is held, every press is refused, and after the next poll Conn reads your newest reviews of the PR: one on the draft's commit submitted at about or after the time the post was sent (up to 5 minutes earlier, for GitHub's clock) is that post, and is recorded as posted; with none, the post can be pressed again. A lookup that fails keeps the post held, to be checked after the next poll. The hold is in memory only: after a restart the post is refused until the PR has been polled, and then a review GitHub took sets the draft aside as reviewed, so it is not posted twice. At most 20 posts are in flight or held at once.
- **Alerts.** A row entering `REVIEW READY` raises one notification, `<repo>#<n> review ready`, its body the verdict and counts (`approve, 3 comments`, `comment, 1 blocker, 3 comments`), once per draft (a rewrite of the file in the same launch does not alert again, a newer launch does), never for the first snapshot after the page opens, and clicking it opens that row. It follows the same alert switch and focus rule as the other alerts.

## Auto-close

Only for sessions conn launched, found by their worktree folder and the launch's name (which `claude --name` registers), so your own session of that name in another folder is never touched. A session is closed when it is `idle` with a visibly empty input box (a typed draft blocks it) and either your review landed on GitHub after the launch, or a review draft of the session is stored and was not set aside (a stored draft counts as a landed review, posted or not), and it has been idle 10 minutes (`CONN_REVIEW_CLOSE_MIN`, 1 to 60), or it has been idle an hour with no review (with GitHub off there is no review to see, so only the hour closes it). A busy session, or one stopped on a prompt, is never closed and restarts the count; the count lives in memory, so a server restart only delays a close. cmux refuses to close a workspace with a running process, so conn closes it with `--force`; the conditions above are what make that safe. The close ends the whole workspace, not only the session: a split pane running a plain shell is closed with it, so conn refuses to close a workspace where another live session is running. A review running inside Conn is closed by stopping its session instead, with no cmux: the screen is read from Conn's own terminal, and the stop is made only while the session runs, is registered and still shows an empty input box. The close does not remove the worktree: it stays while the PR is open, so History's `RESUME` can reopen the session in it. A sweep removes it afterwards: after each successful GitHub poll, conn goes through the launch records in `reviews.json` (so a PR that ended while the server was down is covered, and no folder name is ever parsed) and removes a launch's worktree with `git worktree remove` (never forced, run in the clone the worktree was made from, as the launch recorded it or, for an older launch, as the worktree's own `.git` pointer names it; when neither says, nothing is removed) only when the PR's own read said it merged, closed or is gone, its repo is allowed and was searched at the last poll (a repo taken off the list, or one whose pattern could not be searched, keeps its worktrees), no review of it is starting, being closed or still open, no review file in the folder waits to be read, no live session is working in the folder, and `git status` is clean (a dirty worktree stays, and is looked at again on each poll). A session that disappears on its own, or never appears within 5 minutes, is just forgotten; its worktree goes the same way once the PR has ended. History keeps the session; `RESUME` reopens it while the worktree exists, and says so when the sweep has removed it.

A review running inside Conn when Conn quit is resumed the next time Conn starts, on its own conversation and model and with the same deny list, when `reviews.json` still holds its launch open (see [Settings](settings.md)). After every start of Conn, even one that resumes nothing, no review is closed or forgotten as gone until the resume is done and for 5 minutes after, since its session may still be coming back: a review that really ended may close up to 5 minutes late, and REVIEW is refused meanwhile for a PR that has an open launch. A start that resumes nothing because sessions are set to open in a terminal or as a command keeps the other sessions' records for later, but not the reviews': once the 5 minutes are over, a review whose session has not come back is closed like any other, and a closed review is never resumed.

## When something is missing

- **`gh` not installed or signed in.** Until GitHub has been read once the tab says why and lists nothing; after that a failing poll keeps the last list and shows the error. The rest of conn is unaffected.
- **Slack signed out or unreadable** (the claude.ai Slack connector needs a login, or a scan failed): there is no fallback to every open PR. The page says `Slack could not be read: showing only PRs that request you` (with the error, or the sign-in hint), and lists only what another source lists: a PR found in a channel or a DM drops out until Slack reads again (its record is kept, so it comes back with its link). With `Every open non-draft PR` on, every open PR is still listed and the page says only Slack's links are hidden. A failed DM scan alone hides only what a DM lists. A channel scan's error is no longer shown once no channel is chosen.
- **Setup, or GitHub off:** the tab is off and says why; nothing is called on GitHub or Slack. Review sessions conn already launched are still closed when they finish (that reads the screen and closes the cmux workspace, or stops a session hosted inside Conn, and saves `closedAt` in `reviews.json`), as the paragraph on closing says. A settings change takes effect at once, without a restart.
- **Every source off:** the page says so and links to Settings.
- **No local clone of a repo:** its rows say so and REVIEW is disabled for them; a clone found later is picked up without a restart.
- **`CONN_REVIEWS_DRY=1`** shows fixed synthetic rows (all six states, both kinds of re-review ask, a bot, a DM-only PR, a merged PR, two repos sharing a PR number, a repo with no clone, and one old record on Settings; the `REVIEW READY` row holds a draft with one finding inside its diff and one outside) with no `gh`, Slack, files or cmux; REVIEW answers without launching anything, and Post review is refused (a dry run posts nothing). With no `settings.json` it starts from the dry seed (see [Dry runs in Settings](settings.md)): nothing is written to `$CONN_DATA`.

Reviews uses `reviews.json` in `$CONN_DATA`, readable only by you (version 2): one record per PR keyed `owner/repo#n` (the Slack match and its channel, the DM link and time, first-seen and last-seen-open times, whether GitHub asked for your review, how it ended, and one record per launch with the clone it was made from, and the review draft the launch's session wrote or why its file could not be read), a cursor per channel and the DM cursor, the leads the scans found that wait to be read (at most 300, a day at most), and the old records it could not place. A record is forgotten 14 days after anything last touched it (placing an old record under a repo counts as a touch), and only once its own read said it is not open and its worktree is gone (a record that holds nothing a source could list again, no request, post, DM or launch, ages out with no read). A record of a repo taken off the allowlist is kept as it is (hidden, never read or pruned) and shows again when the repo is allowed again. Every save also sets the data directory itself (`~/.config/conn` by default) to owner-only (0700), so an existing one that was more open becomes private. With GitHub off, conn still reads a version 2 `reviews.json` once at start, so that review sessions it launched are closed when they finish (an older file is left as it is until the allowlist is saved). It can be deleted; the next scan looks back 2 days again. A `reviews.json` conn cannot use (unreadable, not JSON, another version) is first copied to `$CONN_DATA/reviews.json.unreadable.bak` (a later one to `.unreadable.2.bak` and on: a copy is never overwritten, and the log names the copy; when it cannot be copied nothing is written over it) and a new one is started. While `reviews.json` cannot be written (a copy could not be made), the page says why, nothing is saved, REVIEW and placing old records answer 409 (a launch that is not saved would be forgotten at the next restart, its worktree never swept), and a settings save or REFRESH opens the file again, so fixing the cause needs no restart.

An older `reviews.json` (version 1, one repo, keyed by number) is migrated once, when the allowlist is first saved (never during setup): it is first copied to `$CONN_DATA/reviews.json.v1.bak` (0600, through a temp file, so a crash never leaves a half copy under that name; when that name holds another file, an earlier migration's copy or anything else, it is kept and the copy goes to `.v1.2.bak` and on, and a copy that is already this very file is used as it is; the migration stops with nothing written when no copy can be made). Version 1 read one review repo, so the file is placed whole: under the repo the `origin` of every launch worktree still on disk names, when they all agree and the list allows it; else, with no worktree left, under the one repo whose name matches the clone folder the launch paths hold, among the exact allowlist patterns and the repos conn has seen that the list covers. Otherwise every record is kept, never listed, and the Settings page lists them (`N old review records conn could not place`) with a field to name the repository of one, or of all at once (`POST /api/reviews/legacy`, `{ number, repo }` or `{ number: "all", repo }`, an allowed repo only). Nothing migrated counts as requested of you: what lists a placed record is what GitHub says at its next read. The migration runs again harmlessly on a version 2 file. If you go back to an older conn after the migration, it reads the version 2 file as empty and its next save replaces it; going forward again migrates that new file, and the records from before are only in `reviews.json.v1.bak` (the second migration's file is in `reviews.json.v1.2.bak`) (copy it back over `reviews.json` by hand, with conn stopped, to migrate them again).

Env for Reviews: `CONN_REVIEW_CLOSE_MIN` (default 10), `CONN_REVIEW_ME` (your GitHub login, default from `gh`) and `CONN_REVIEWS_DRY=1`. Reviews reads no repository, channel, DM switch or clone folder from the environment: they come from Settings (the older review variables are no longer read by Reviews). The rest of its values (the prompt and the re-review line, the poll interval, the first-scan window, the scan intervals, the scan model, budget and timeout, the one-hour cap, the review name pattern) live in `internal/config/config.go` (the prompt and the re-review line in `internal/config/prompts.go`).

- the first real `REVIEW` click with a real review session, with and without the `/deep-code-review` skill installed (the launch path was tried by hand with a throwaway skill; Conn's skill has a mode that writes the review file and posts nothing when the prompt says to, but a skill of your own by that name may ask first or post by its own rules, and the one-hour cap closes a session that is waiting on you);
- a real post: Post review was run only against fakes (the request and the review body are golden files), never against GitHub, so whether GitHub accepts the comments' lines as Conn places them, an `APPROVE` on someone else's PR, the review's URL, and the check after an unclear failure are untested; and a real review session writing `.conn/review.json` from the new prompt (the file's reading was tested on written files, not on a model's);
- the Slack thread-reading path, which finds re-review asks made in a thread, against real Slack (only the channel read was measured);
- the DM scan against real Slack (the search filters and the helper's answer shape are what the prompt asks for; only fakes were run, so whether `slack_search_public_and_private` honours `channel_types "im"`, `include_bots false` and a unix `after:` as the prompt assumes is unconfirmed);
- auto-close against a real cmux, or inside Conn, with a real review landing; a review resumed at launch with a real `claude --resume`;
- the worktree sweep against real git worktrees (its tests use a fake git and temp folders), and the helper's full argument list against the real `claude` (its tests check the arguments it is started with; a short form of the `--tools` and `--disallowedTools` flags was run once and accepted);
- the owner-only directory mode: every save of `reviews.json` sets `$CONN_DATA` to 0700, so an existing `~/.config/conn` that was more open becomes owner-only. That is what the code does and the tests show it on a temp directory; it was not observed on a real `~/.config/conn`.

Known gaps: a PR that asks for your review on GitHub but whose Slack post was not found (the chase is spent, or no dashboard was open) is listed without a Slack link; the `user:` search qualifier for an `owner/*` pattern and the batched reads by number were checked by hand against a public repo, not against a private organization; a session that is cleared (`/clear`) after a server restart is no longer auto-closed.
