# Reviews

The `REVIEWS` tab lists the pull requests that want your review, in every allowed repository, and starts a full review session for one with a click (a Claude Code session told to review that PR, using a `/deep-code-review` skill when you have one installed). It lists an open, non-draft PR of an allowed repo that you did not write when a review source that is on lists it (Settings > Reviews): GitHub asks for your review (`Requests me`, on by default; a PR stays listed after your review drops the request), it was posted in one of the chosen Slack channels (Slack on, at least one channel), it was sent to you in a Slack DM (Slack on and the DM switch on), or `Every open non-draft PR` is on. A PR is never listed because of a source that is off, and a bot's PR counts like anyone's. A PR that merged or closed stays listed, greyed, for a day, but only one you had touched (posted, DM'd, reviewed by you, or launched from here). Every row shows its repository, the number (linked to GitHub), the title as plain text, the author, its age, the checks, the state, the Slack links and any tags; sessions you launched link to their Overview page. The same number in two repositories is two rows. The state is derived from GitHub (your latest review and the commit it was made on, review requests), never typed in:

- `NEW`: listed, you have no review on it.
- `REVIEWING`: the session a REVIEW press launched for it is live (found from the launch record, never from a session's name).
- `WAITING`: your latest review is comments or changes requested, and nobody has asked again.
- `RE-REVIEW`: you reviewed before and the author asked again, either by re-requesting you on GitHub or by saying so in the Slack thread of the post. The tag says which: `RE-REVIEW REQUESTED (GITHUB)` or `(SLACK)`.
- `DONE`: your latest review is an approval, or the PR merged or closed.

`UPDATED` shows when the PR's head moved past the commit you reviewed (with no ask yet it stays `WAITING`; after an approval it stays `DONE`). `NOT IN A CHANNEL` shows on a row that only `Every open non-draft PR` lists while the channel scan is on. Rows sort `RE-REVIEW`, `NEW`, `REVIEWING`, `WAITING`, `DONE`, the most recently updated first within a state, and the filter bar has Status and Author. The tab's badge is the number of `NEW` and `RE-REVIEW` rows (marked seen per `owner/repo#n`).

## How it finds things

- **GitHub, free.** Nothing is called in setup or while the GitHub module is off. Otherwise the server polls (whether or not a dashboard is open, and at once when a setting a poll reads changes) with `gh api graphql`, every 3 minutes, or less often when GitHub says a poll is dear: the interval comes from what the last poll cost (the `rateLimit` GitHub answers with, so it counts what the poll really read: the searches, six to a call, and the tracked PRs read by number), long enough that an hour of polls spends at most half of the 5,000 hourly GraphQL points and at most half of what is left before the reset, and never longer than 15 minutes. `MY PRS` polls GitHub as the same account, so while both are polling they share that half between them (each waits as if it had half the budget; one that stopped asking an hour ago, or whose module is off, takes no share). Many patterns with only `Requests me` on cost little and poll every 3 minutes. It runs the `Requests me` search for each pattern (`is:pr is:open archived:false user-review-requested:@me` plus `repo:owner/repo` for an exact pattern or `user:owner` for `owner/*`, 100 each; an exact pattern an owner wildcard of the list already covers is not searched again), and when `Every open non-draft PR` is on one more search per pattern (`is:pr is:open draft:false archived:false -author:@me`, at most 200 each; a list cut off there is a notice on the page, never a reason to drop anything). Searches go at most six to a call, and each PR asks for at most 20 review requests, 20 latest reviews and 50 check contexts, so no call nears GitHub's node limit. Then every PR conn tracks in an allowed repo that the searches did not return, and that a source that is on could list, is read by number, in batched `gh api graphql` calls of 50; that read says whether it is open, merged, closed or gone, so a PR is never taken as ended because a list left it out, and a record whose read did not answer is kept as it was. Every PR that comes back is checked against the allowlist again, and again when the page shows it. A pattern GitHub cannot search (a typo, a repo you lost access to, an org's SAML rule) is listed in a notice and its repos' rows stay as they were, marked out of date, with REVIEW refused for them; the other patterns go on. When GitHub says the rate limit is used up, Reviews asks it nothing more until the reset, keeps the list and says so; `MY PRS` waits for the same reset, and the other way round. Your login comes from `gh api user` (`CONN_REVIEW_ME` overrides it).
- **Slack, only when needed.** With Slack on and at least one channel chosen, a short Haiku run with only the read-only Slack tools (no Bash) reads every chosen channel in one run, each from its own cursor, for the posts that announce a PR of an allowed repo (the prompt names the channels and the allowed repos, an `owner/*` pattern as "any repo owned by owner"). Every helper conn starts has no built-in tools beyond the ones listed for it (`--tools` is set to exactly those, none for this one), so your own `permissions.allow` rules, such as a `Bash(...)` rule, cannot give it a shell. It runs only while a dashboard is open: for a tracked PR with no post matched yet at 0, 10, 30 and 90 minutes after it was first seen, and otherwise at most every 10 minutes to find new posts (at once on REFRESH). A channel's first scan looks back 2 days; after that it reads from its cursor, which every completed run moves to that run's start less 15 minutes (or to a newer post), pulled back, while PRs still have no post, to 15 minutes before the older of the cursor and the earliest of those PRs' first-seen times. It never reads further back than the 2-day window, whatever the cursor (an old one, or a channel chosen again, reads the window). For a `WAITING` PR whose head moved past your review and that has a matched post, the same run also reads the post's thread for a re-review ask made after your review, on the same 0/10/30/90 schedule counted from when the head moved. Whatever the helper returns is checked before use: a post counts only in a chosen channel, with an `https://…slack.com/` permalink, and when its PR link names an allowed repo (a valid `owner/repo`; any other is dropped and never fetched). A post about a PR conn does not know yet is a lead: it is kept in `reviews.json` and read by number from GitHub (at most 30 per scan, the rest at the next) and counts only when GitHub has it open in an allowed repo, so a message cannot invent a PR. A lead is read with the settings as they are then (not as they were when the scan began), and a draft or a PR of your own that a post names is dropped. A scan that finishes after Slack, GitHub or every channel (for the DM scan: the DM switch) was turned off is dropped whole: nothing it read is kept, no cursor moves, and the Slack card records nothing.
- **Slack DMs, only when needed.** People often ask for a review in a DM instead of the channel, so a second, separate Haiku run (same read-only Slack tools, no Bash) searches your 1:1 direct messages for messages that link a pull request of an allowed repo (it runs only with Slack on and the DM switch on in Settings). Only DMs sent to you by a person count: never a bot, a group DM or a channel, and never what you wrote. It reports the message's Slack timestamp, its link, the PR URL and whether you sent it (a message you sent is dropped here), and nothing else: the text of a DM is not returned, stored or shown, and the prompt holds only the allowed repos, a timestamp and fixed rules. A DM counts only when it names a PR of an allowed repo that GitHub has open (a lead, read by number like a channel post's), and it lists that PR with a small `DM` link to the first such message; a later DM after your own review is a re-review ask (`RE-REVIEW REQUESTED (SLACK)`, not for an approved PR), like a later message in the channel thread. It runs while a dashboard is open, at most every 10 minutes and at once on REFRESH, reading from its cursor less 15 minutes, never further back than the 2-day first window (which is also where the first run starts). The time limit goes to Slack's search as its own `after` parameter in Unix seconds, not as a date filter, and the helper follows the result cursor for at most 5 pages. A signed-out Slack is the same state for both scans (only the Slack connector counts: another connector being signed out, such as Atlassian, does not), and a DM scan that reports it makes the next DM scan wait as long as the channel scan does. A DM scan that reads successfully while Slack shows as signed out clears that state, and never an error of the channel scan; any other DM failure shows its own banner and leaves the channel scan's state alone.
- **Cost.** One real scan of a day of the channel cost about $0.016 cold (7 posts, 20 s, Haiku). A scan is capped at $0.50 and 90 s. Re-review asks in Slack threads are not part of that measurement.

## REVIEW

`REVIEW` (`RE-REVIEW` on a re-review row) takes a `SONNET | OPUS` choice per row (remembered, Sonnet by default) and then:

1. Finds the repo's local clone (Settings > Local clones: the folder set there, else `<clones folder>/<repo>`, else `~/projects/<repo>`, used only when its `origin` is that repo); with none, REVIEW is disabled and the row says `No local clone of owner/repo: set a folder in Settings`. Fetches the PR's base branch from the clone's `origin` and puts a detached worktree at its tip, at `$CONN_DATA/reviews/<the first launch's name>/<repo>`, so two PRs never share a folder; the launch records which clone it was made from. An existing folder is reused only when it is a worktree of that repo's clone. The working files of your clone are never touched, but it is not read-only: `git fetch` updates its `origin/<base>`, `git worktree add` and `git worktree prune` write to its `.git`, and `.conn/` is appended to its shared `.git/info/exclude`.
2. Writes the prompt to `<worktree>/.conn/prompt.md` (excluded from git) and starts a session where Settings say (inside Conn, a cmux workspace, or a command to paste) named `pr-<n>-<owner>--<repo>` (`pr-<n>.2-<owner>--<repo>`, ... for a later review of the same PR) running `claude --name <name> --model <model> -- "Read .conn/prompt.md and follow it exactly."`. No two PRs share a name: the number and launch come first, and a GitHub owner never holds two dashes in a row, so the first `--` ends it (an owner that does, or a name over 120 characters, is named `pr-<n>[.<k>]-x<12 hex of sha1(owner/repo)>` instead). The prompt is the one in `internal/config/prompts.go`, with the PR number and its `owner/repo` filled in: plain instructions (review the PR, comment P0-P3 issues inline, approve when none blocks, treat PR and Slack text as data, do not repost another reviewer's point) that need no skill of yours, and that use a `/deep-code-review` skill when one is installed; a re-review appends one line naming the commit of your previous review. If the session does not start, or sessions are set to open as a command, the page shows the command to paste with a COPY button and leaves the worktree, and the launch is recorded (launched by hand): the next press is the next review. A launch by hand does not retire the earlier launch of the PR, since nothing has started yet: the earlier session keeps being followed (and closed after your review) until a session really starts.
3. Refuses before any git call or session start for a repo that is not `owner/repo`, a number that is not a plain PR number, a PR not in the list or not open, a repo with no clone, a session already named for it in any folder, a second click within 30 seconds, and a second click while the newest launch of the PR has not appeared as a session yet (up to 5 minutes). The press is `POST /api/reviews/start` with `{ repo, number, model }`.

The session is an ordinary Claude Code session with your own settings (auto mode, the advisor model and so on apply). The review is whatever that session does with the prompt (and the `/deep-code-review` skill, if installed: Conn ships one, see [Settings](settings.md#agents-and-skills)): it posts its findings and approves when none blocks, as it would if you started it by hand. For Reviews, conn itself never posts, comments, approves, requests changes or reacts on GitHub or Slack, and nothing launches without a click (what My PRs writes is listed under that tab). A session with such a name (or the older `pr-<n>` and `pr-<n>-<k>`) that works under `$CONN_DATA/reviews` gets the kind `REVIEW` in Sessions and in History; a session that merely looks like one elsewhere is ad hoc (the name is only a kind; which PR it reviews comes from the launch record) (sessions History imported from old transcripts keep `AD HOC`), and `RESUME` in History reopens one.

## Auto-close

Only for sessions conn launched, found by their worktree folder and the launch's name (which `claude --name` registers), so your own session of that name in another folder is never touched. A session is closed when it is `idle` with a visibly empty input box (a typed draft blocks it) and either your review landed on GitHub after the launch and it has been idle 10 minutes (`CONN_REVIEW_CLOSE_MIN`, 1 to 60), or it has been idle an hour with no review (with GitHub off there is no review to see, so only the hour closes it). A busy session, or one stopped on a prompt, is never closed and restarts the count; the count lives in memory, so a server restart only delays a close. cmux refuses to close a workspace with a running process, so conn closes it with `--force`; the conditions above are what make that safe. The close ends the whole workspace, not only the session: a split pane running a plain shell is closed with it, so conn refuses to close a workspace where another live session is running. A review running inside Conn is closed by stopping its session instead, with no cmux: the screen is read from Conn's own terminal, and the stop is made only while the session runs, is registered and still shows an empty input box. The close does not remove the worktree: it stays while the PR is open, so History's `RESUME` can reopen the session in it. A sweep removes it afterwards: after each successful GitHub poll, conn goes through the launch records in `reviews.json` (so a PR that ended while the server was down is covered, and no folder name is ever parsed) and removes a launch's worktree with `git worktree remove` (never forced, run in the clone the worktree was made from, as the launch recorded it or, for an older launch, as the worktree's own `.git` pointer names it; when neither says, nothing is removed) only when the PR's own read said it merged, closed or is gone, its repo is allowed and was searched at the last poll (a repo taken off the list, or one whose pattern could not be searched, keeps its worktrees), no review of it is starting, being closed or still open, no live session is working in the folder, and `git status` is clean (a dirty worktree stays, and is looked at again on each poll). A session that disappears on its own, or never appears within 5 minutes, is just forgotten; its worktree goes the same way once the PR has ended. History keeps the session; `RESUME` reopens it while the worktree exists, and says so when the sweep has removed it.

A review running inside Conn when Conn quit is resumed at the next launch, on its own conversation and model, when `reviews.json` still holds its launch open (see [Settings](settings.md)). While a launch resumes, and for 5 minutes after, no review is closed or forgotten as gone, since its session may still be coming back: a review that really ended may close up to 5 minutes late, and REVIEW is refused for a PR that has an open launch. A launch that resumes nothing because sessions are set to open in a terminal or as a command keeps the other sessions' records for later, but not the reviews': once the 5 minutes are over, a review whose session has not come back is closed like any other, and a closed review is never resumed.

## When something is missing

- **`gh` not installed or signed in.** Until GitHub has been read once the tab says why and lists nothing; after that a failing poll keeps the last list and shows the error. The rest of conn is unaffected.
- **Slack signed out or unreadable** (the claude.ai Slack connector needs a login, or a scan failed): there is no fallback to every open PR. The page says `Slack could not be read: showing only PRs that request you` (with the error, or the sign-in hint), and lists only what another source lists: a PR found in a channel or a DM drops out until Slack reads again (its record is kept, so it comes back with its link). With `Every open non-draft PR` on, every open PR is still listed and the page says only Slack's links are hidden. A failed DM scan alone hides only what a DM lists. A channel scan's error is no longer shown once no channel is chosen.
- **Setup, or GitHub off:** the tab is off and says why; nothing is called on GitHub or Slack. Review sessions conn already launched are still closed when they finish (that reads the screen and closes the cmux workspace, or stops a session hosted inside Conn, and saves `closedAt` in `reviews.json`), as the paragraph on closing says. A settings change takes effect at once, without a restart.
- **Every source off:** the page says so and links to Settings.
- **No local clone of a repo:** its rows say so and REVIEW is disabled for them; a clone found later is picked up without a restart.
- **`CONN_REVIEWS_DRY=1`** shows fixed synthetic rows (all five states, both kinds of re-review ask, a bot, a DM-only PR, a merged PR, two repos sharing a PR number, a repo with no clone, and one old record on Settings) with no `gh`, Slack, files or cmux; REVIEW answers without launching anything. With no `settings.json` it starts from the dry seed (see [Dry runs in Settings](settings.md)): nothing is written to `$CONN_DATA`.

Reviews uses `reviews.json` in `$CONN_DATA`, readable only by you (version 2): one record per PR keyed `owner/repo#n` (the Slack match and its channel, the DM link and time, first-seen and last-seen-open times, whether GitHub asked for your review, how it ended, and one record per launch with the clone it was made from), a cursor per channel and the DM cursor, the leads the scans found that wait to be read (at most 300, a day at most), and the old records it could not place. A record is forgotten 14 days after anything last touched it (placing an old record under a repo counts as a touch), and only once its own read said it is not open and its worktree is gone (a record that holds nothing a source could list again, no request, post, DM or launch, ages out with no read). A record of a repo taken off the allowlist is kept as it is (hidden, never read or pruned) and shows again when the repo is allowed again. Every save also sets the data directory itself (`~/.config/conn` by default) to owner-only (0700), so an existing one that was more open becomes private. With GitHub off, conn still reads a version 2 `reviews.json` once at start, so that review sessions it launched are closed when they finish (an older file is left as it is until the allowlist is saved). It can be deleted; the next scan looks back 2 days again. A `reviews.json` conn cannot use (unreadable, not JSON, another version) is first copied to `$CONN_DATA/reviews.json.unreadable.bak` (a later one to `.unreadable.2.bak` and on: a copy is never overwritten, and the log names the copy; when it cannot be copied nothing is written over it) and a new one is started. While `reviews.json` cannot be written (a copy could not be made), the page says why, nothing is saved, REVIEW and placing old records answer 409 (a launch that is not saved would be forgotten at the next restart, its worktree never swept), and a settings save or REFRESH opens the file again, so fixing the cause needs no restart.

An older `reviews.json` (version 1, one repo, keyed by number) is migrated once, when the allowlist is first saved (never during setup): it is first copied to `$CONN_DATA/reviews.json.v1.bak` (0600, through a temp file, so a crash never leaves a half copy under that name; when that name holds another file, an earlier migration's copy or anything else, it is kept and the copy goes to `.v1.2.bak` and on, and a copy that is already this very file is used as it is; the migration stops with nothing written when no copy can be made). Version 1 read one review repo, so the file is placed whole: under the repo the `origin` of every launch worktree still on disk names, when they all agree and the list allows it; else, with no worktree left, under the one repo whose name matches the clone folder the launch paths hold, among the exact allowlist patterns and the repos conn has seen that the list covers. Otherwise every record is kept, never listed, and the Settings page lists them (`N old review records conn could not place`) with a field to name the repository of one, or of all at once (`POST /api/reviews/legacy`, `{ number, repo }` or `{ number: "all", repo }`, an allowed repo only). Nothing migrated counts as requested of you: what lists a placed record is what GitHub says at its next read. The migration runs again harmlessly on a version 2 file. If you go back to an older conn after the migration, it reads the version 2 file as empty and its next save replaces it; going forward again migrates that new file, and the records from before are only in `reviews.json.v1.bak` (the second migration's file is in `reviews.json.v1.2.bak`) (copy it back over `reviews.json` by hand, with conn stopped, to migrate them again).

Env for Reviews: `CONN_REVIEW_CLOSE_MIN` (default 10), `CONN_REVIEW_ME` (your GitHub login, default from `gh`) and `CONN_REVIEWS_DRY=1`. Reviews reads no repository, channel, DM switch or clone folder from the environment: they come from Settings (the older review variables are no longer read by Reviews). The rest of its values (the prompt and the re-review line, the poll interval, the first-scan window, the scan intervals, the scan model, budget and timeout, the one-hour cap, the review name pattern) live in `internal/config/config.go` (the prompt and the re-review line in `internal/config/prompts.go`).

## Not verified

The tab was checked in a real browser only against the dry-mode data, and the parts below were not run against the real thing:

- the first real `REVIEW` click with a real review session, with and without the `/deep-code-review` skill installed (the launch path was tried by hand with a throwaway skill; Conn's skill posts and approves without stopping to ask when the prompt says to, as Reviews' prompt does, but a skill of your own by that name may ask first, and the one-hour cap closes a session that is waiting on you);
- the Slack thread-reading path, which finds re-review asks made in a thread, against real Slack (only the channel read was measured);
- the DM scan against real Slack (the search filters and the helper's answer shape are what the prompt asks for; only fakes were run, so whether `slack_search_public_and_private` honours `channel_types "im"`, `include_bots false` and a unix `after:` as the prompt assumes is unconfirmed);
- auto-close against a real cmux, or inside Conn, with a real review landing; a review resumed at launch with a real `claude --resume`;
- the worktree sweep against real git worktrees (its tests use a fake git and temp folders), and the helper's full argument list against the real `claude` (its tests check the arguments it is started with; a short form of the `--tools` and `--disallowedTools` flags was run once and accepted);
- the owner-only directory mode: every save of `reviews.json` sets `$CONN_DATA` to 0700, so an existing `~/.config/conn` that was more open becomes owner-only. That is what the code does and the tests show it on a temp directory; it was not observed on a real `~/.config/conn`.

Known gaps: a PR that asks for your review on GitHub but whose Slack post was not found (the chase is spent, or no dashboard was open) is listed without a Slack link; the `user:` search qualifier for an `owner/*` pattern and the batched reads by number were checked by hand against a public repo, not against a private organization; a session that is cleared (`/clear`) after a server restart is no longer auto-closed.
