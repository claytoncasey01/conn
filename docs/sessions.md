# Watching and answering sessions

- **Needs input.** A session stopped on a permission prompt, a question or a dialog shows as `NEEDS INPUT` (with what it is waiting for), sorts first, and has its own filter. The status comes from the session registry's `waiting` / `waitingFor`.
- **Alerts.** The `ALERTS` button turns on notifications for a session that needs input or finishes, a run with questions, PR checks or merges (each repository's PR of a run on its own), and a My PRs row with a Slack draft to post. In a browser they are the browser's notifications; in `Conn.app` they are macOS notifications (see [the app](../README.md#the-app)). They only fire while the tab is in the background (in the app, while its window is hidden or not in front), and only on a change (never for what was already true when the tab opened). The tab title carries the count of things waiting on you either way (sessions on a prompt, runs with questions, and My PRs rows that need you). The first time alerts are turned on, the browser or macOS asks whether Conn may show notifications, and neither asks again after a no. Settings has an Alerts row, at first launch too, that says what is allowed and the one thing to do about it: turn alerts on or off, or, after a no, where to change it (System Settings for the app, which Settings opens; the browser's site settings for a page). The row and the button read the permission again each time the window comes back to the front, so a change made there shows without a reload.
- **Reply.** `REPLY` in a session's footer types a message into that session's terminal. For a session running inside Conn (see [below](#sessions-inside-conn)) that is Conn's own terminal: the message is typed only into an input box the screen shows empty, and only while the screen is still that one when the message's turn to be typed comes. For a session in cmux it is that session's cmux terminal, offered only when the session's own environment names a cmux surface *and* the cmux app is an ancestor of the process (a `claude --bg` session started from a cmux terminal inherits that terminal's ids but has no terminal), and it sends only while the CLI owns its terminal (not suspended with Ctrl+Z or exiting: the same surface then shows your shell, whose prompt may also be `❯`) and only into Claude's input box when it is visibly empty (cmux does not reliably refuse to type over a draft). Either way it refuses text starting with `!` or `/`, a control character other than a line break, and anything while the session is stopped on a permission prompt or dialog: those are answered on the agent page (below), where the footer points.
- **Cost.** Each session and agent shows an estimated cost from the transcripts' token counts at list prices (cache writes by 5-minute and 1-hour, advisor calls on the advisor's model). It is an estimate, not a bill. Responses are counted once by message id: a transcript repeats each response's usage on every content-block line.
- **Advisor.** The advisor model shown with a session is the one it runs: what its transcript says its advisor is set to, else the model of its latest advisor call, else none (`—`). Claude Code sets the advisor when a session starts and keeps it on a resume.
- **Teammates.** A Claude Code teammate (an agent started with a name, running as its own `claude` in its own pane) is not a subagent: it writes a transcript of its own. conn finds the teammates of a session by the team name and teammate name its transcript spawned them into (a `teammate_spawned` result), looking for transcripts tagged with that team and name in the same project folder, and lists them as agents of the lead, tagged `TEAMMATE`, in the tree, the agent pages and History. Their cost, calls, errors and log lines are counted in the lead's totals, and a teammate's own subagents are listed under it (one level deeper). A teammate that also runs as a live session of its own keeps its row, with its real status, reply box and alerts, tagged `TEAMMATE` with a link to its lead; it is left out of the Sessions page's cost and advisor-call sums (the lead's row already has it), and it is never archived on its own while a transcript in its folder that spawned its team is on disk (that need not be a file named like the team: a resumed lead has a new id), so History counts it once. A teammate that keeps running after its lead has ended is not added to the lead's finished History entry (that entry is written once, when the lead ends). Limits: a teammate is found only in its lead's own project folder (one started in another folder is an ordinary session), and History entries written before this existed are not rewritten (an old teammate entry stays as it was; backfill replaces an entry only when its transcript grew). Rows written by a build before this one can therefore list a teammate twice: as an entry of its own and inside its lead's entry.

## Answering from the agent page

A waiting agent's page opens with a `NEEDS INPUT` panel: which agent, why it waits, for how long, and what it is asking, read from the session's terminal screen (Conn's own model of the screen for a session inside Conn; cmux `read-screen` for a session in cmux, only while the session is waiting, a dashboard tab is open and the CLI owns its terminal: a session suspended with Ctrl+Z shows no ask, since the screen is then the shell's) and shown as plain text. The agent switcher marks a waiting agent `NEEDS INPUT` on every agent page and sorts it first, the Overview draws its card first however long it has waited (the lead, or a teammate waiting in its own session; a subagent is not marked, since it may be running while its lead waits on a prompt of its own), and the notification names the agent and the question and opens its page (it stays quiet while the dashboard is the window in front). What the panel offers depends on what the screen is:

- **A pick-list question:** one button per option.
- **A permission prompt:** exactly two buttons, `ALLOW ONCE` and `DENY`, with the command beside them. `always allow` and `switch to auto mode` are never offered; they stay in the terminal. The whole command is shown, up to half the window, then it scrolls with how many lines are left over the buttons, and `ALLOW ONCE` stays disabled until such a command has been scrolled to its end.
- **The empty input box** while the registry still says the session waits (a moment the screen has not caught up, or Claude waiting for your next message): the reply box above.
- **Anything else** (a screen of a waiting session that is not a dialog it reads, such as a plan approval (shown as the screen's text under its last rule; not yet seen on a real session); a dialog it does not recognise, several questions at once, a list of more than 7 options or with keys other than 1 to 9, an Edit or Write permission, or a terminal shared by two sessions in one cmux workspace): the text of the screen and an `OPEN TERMINAL` button, which only brings that session's cmux workspace to the front. For a session inside Conn the terminal is the panel on the page: answer it there.
- **A subagent's page** says it is waiting through the lead and links to the lead's page (a subagent of a teammate that runs in a session of its own: through that teammate, and only while it waits). A session with no terminal Conn can read (neither inside Conn nor in cmux) shows the state and says it cannot be answered here.

Safety, because the screen is untrusted text and can change between what you saw and your click:

- A choice is sent with the id of the prompt it showed (the free-text reply goes through the reply box, which sends no id and has the reply guards above). The server reads the screen again and parses it right before sending, and refuses with HTTP 409 unless it is the same prompt (it also refuses a prompt it just answered, a session that moved on, or one that is not in the foreground of its terminal).
- The answer is one digit key, with no Enter, never text built from the screen: for a session in cmux it is sent with `cmux send`, with no `--force`; for a session inside Conn it is typed by Conn's own terminal, which checks once more, when the key's turn to be written comes, that the screen still shows that prompt and nothing else was typed in between. The page shows the screen only as text, never as HTML, with bidi, zero-width, tag, line-separator and control characters (other than newline and tab) made visible.
- No button is pre-selected or focused, Enter sends nothing, buttons are disabled while a request is out, and they stay disabled for 700 ms after the prompt shown changes (a prompt that changes under the pointer cannot be hit by a click aimed at the old one).
- After a 409 or an error the panel shows what it says and never resends; the prompt a 409 reports is shown until the next snapshot. After a send it stays locked until the screen moves on, and offers `OPEN TERMINAL` if it has not after 8 seconds. After a 502 or a request lost on the way the key may or may not have been pressed: the panel locks that prompt at once, says so, and offers `OPEN TERMINAL`.
- The server remembers the prompt it last answered in each session (by session, status time and id) and refuses it again until the terminal moves on. A send that failed or timed out leaves no such mark, so a retry stays possible even if the key did land; the re-read before it still has to match.
- Two prompts that look exactly alike and follow each other with no change of status in between (two subagents asking to run the same command, queued) get the same id, because the id is made from what the screen shows and the registry's status time, and neither tells them apart. A click meant for the first can then answer the second. What is approved is exactly what was shown (the same command, once, never a standing permission); only which request it answers can differ. The terminal itself shows nothing more to tell them apart.
- `REPLY` has no shared-workspace rule, unlike these buttons: it types into the exact surface its own session's environment names, so teammates that share a workspace with their lead keep their reply box. The buttons are stricter by design: in a shared workspace a dialog is shown as text with `OPEN TERMINAL`, never answered with one key.

Requirements: the session runs inside Conn, or in cmux (as for `REPLY`). A permission prompt only appears in the default permission mode; in auto mode Claude does not prompt, so there is nothing to answer. The registry must name the wait the way the screen does (`permission prompt` for a permission, `input needed` for a question); a mismatch (a sandbox or worker dialog drawn like a permission prompt) falls back to text and `OPEN TERMINAL`.

Routes: `<id>` is the process id, or the id Conn gave a session inside Conn. `POST /api/sessions/<id>/answer` takes `{ "askId": "...", "choice": "1" }` (the option's key, as a string) or `{ "askId": "...", "text": "..." }`, and answers 200, 400 for bad input, 409 with `{ error, ask }` when the prompt is not the one shown (the `ask` the snapshot would show), 409 with `ask: null` for a session that is not waiting (refused before anything is run) or whose process has ended (before the send: nothing was sent; during it: what reached the terminal is not known), 413 for a body over 64 KB, or 502 when cmux failed (its first stderr line, or a fixed message; never the command line) or a session inside Conn is not taking input. `POST /api/sessions/<id>/terminal` (no body) selects the session's cmux workspace, and does nothing for a session inside Conn. Both need the `x-conn: 1` header, as the other POSTs do. Each session in the snapshot carries `ask` (the parsed prompt, or null) and `sessionId` (the Claude session uuid, which is how a teammate's agent is matched to its own session; `id` is the process id, or the id Conn gave a session inside Conn, which then also carries `hosted: true`).

## Sessions inside Conn

A session Conn starts runs inside Conn unless Settings say otherwise ([Where sessions open](settings.md)). It is a row like any other, with the id Conn gave it in place of a process id, and a Terminal panel on the Sessions page and on the Open work run page: the live screen, the keyboard, a resize, and a control to close the panel. A panel opened late draws the output kept so far (up to 4 MiB), then the live output. Up to 4 panels can show one session at once, and all see the same screen. The terminal takes its colours from the theme.

- **Assistive technology.** The terminal itself is not rendered for a screen reader (xterm.js's screen-reader mode is off); the ask panel, the reply box and the session rows are. A follow-up may add a setting for it.
- **The row is linked by process id.** Conn matches the program it started to Claude Code's own registry by that program's process id, so `CONN_CLAUDE` must be `claude` itself, or a wrapper that `exec`s it. Until claude registers, the row says "Not linked to a Claude session yet" and cannot be replied to.
- **Interrupt.** A panel that closed because the program printed faster than the page could draw offers **Interrupt**, as the hosted Sessions card does while the program runs. It types Ctrl-C into the program. A second press within 3 seconds is not sent, since two Ctrl-C close together make claude quit.
- **Stop.** Stopping a session inside Conn stops its program and everything in its process group: SIGTERM, then SIGKILL after 5 seconds.
- **New session.** The **New session** button beside the Sessions page's filters starts a plain `claude` session. Choose a repository and, if you like, type a name, then press **Start** (Escape or **Cancel** closes the form). The list holds the repositories on your allowlist that have a local clone, found the way Open work finds one (a clone set in Settings, else a folder named for the repository under the clone folder or `~/projects`); with none, the form says to set a clone in Settings. Conn starts `claude --session-id <a new UUID>` in that clone, with `--name <name>` when you typed one. The name is refused if it holds a control, bidi or invisible character, is longer than 256 bytes (counted in UTF-8, as the form also counts it before it sends), or has no letter or digit, and is otherwise reduced to ASCII letters, digits, `.`, `_` and `-` and cut to 64 characters (so `fix the widget` becomes `fix-the-widget`, and a letter outside ASCII is dropped); without one the session is called after the repository. It opens where Settings say: inside Conn its terminal opens on the page; in a terminal it opens a cmux workspace; as a command the form shows the line to paste. A second start in the same repository within 10 seconds is refused, so a double press starts one session, and a session inside Conn is refused while Conn already runs 12. In a dry run (any `CONN_*_DRY` switch) nothing starts: the form shows the command it would have run. A clone set in Settings may be a link: Conn resolves it and runs the session in the real folder. That folder must be yours and no one else's to write, its `.git` a real folder (not a link, and not a worktree's or a `--separate-git-dir` clone's pointer file), and every folder above it a real folder of yours or root's that no one else may write; otherwise the start is refused with the part to fix. A folder your private group may write (its id your own group id, listed in `/etc/group` under your name, with no other member, as a umask of 002 on Debian, Ubuntu or Fedora gives) counts as yours alone; a shared group such as macOS's `staff` does not. A sticky folder above, such as `/tmp`, is fine. The clone's `.claude` and `.git/hooks` folders, when there, must pass the same rule; what is in them, and in `.mcp.json` or `CLAUDE.md`, is not checked. Every problem is reported at once. The check runs again right before the start. See [SECURITY.md](../SECURITY.md#sessions-inside-conn).
- **A new session after a quit.** Inside Conn, a new session is recorded like one resumed from History, on the conversation id Conn chose. The next launch resumes it with History's own checks: the archive must hold that conversation in the same folder, with its transcript, and the repository must still be allowed. So a session you quit before typing anything (claude has written no transcript yet) is not resumed, and nothing is resumed while History is off.
- **Quit and launch.** Closing the app's window keeps every session running. Quitting Conn stops them all, after writing the list of those that ran to `hosted.json`. The next launch resumes them, each on its own conversation, once its owner has checked it again, and a banner says "Resumed N sessions that ran when Conn quit", names them, and offers **Stop all** (which asks first, stops each one whatever it is doing, and lists any it could not stop) and **Dismiss**. The rules, the checks and the limits are in [SECURITY.md](../SECURITY.md#sessions-inside-conn).

Routes, all behind the API's secret like every `/api` route: `GET /api/term/<id>`, a WebSocket (its handshake carries the secret as the subprotocol `conn.key.<secret>`, beside `conn.term.v1`, and must carry the server's own `Origin`), over which the page sends `{"t":"input","d":"..."}` and `{"t":"resize","cols":C,"rows":R}`, and receives the output as binary frames and `{"t":"replay-end"}`, `{"t":"paste-closed"}` and `{"t":"exit","code":N}` as text; `POST /api/term/<id>/interrupt` (no body); `PUT /api/term/background` with `{"background":"#rrggbb"}`, the colour the page draws the terminal on, which Conn answers when a program asks for it; `GET /api/sessions/new`, which answers `{"repos":["owner/name",...],"where":"inside","dry":false}`; `POST /api/sessions/new` with `{"repo":"owner/name","name":"optional"}` (any other field is refused; it needs `x-conn: 1` and the page's own `Origin`), which answers `{"ok":true,"id":"<host id>"}` inside Conn, `{"ok":true}` in cmux, `{"ok":false,"error":...,"manualCommand":...}` when the command is shown instead (or `{"ok":false,"error":...}` with no `manualCommand` when there is no line to paste), `{"ok":true,"dry":true,"command":...}` in a dry run, and `{"error":...}` with 400 (a body or name it does not take, a repository off the allowlist), 403 (no `x-conn: 1` or no `Origin`), 405 (a method other than GET or POST), 409 (no clone, a folder that is not safe, a start just made there, the host full), 413 (a body over 64 KiB) or 500 (a failure inside the server) when it is refused; and `POST /api/sessions/<id>/stop` with `{"force":false}` (a busy session is refused with 409) or `{"force":true}` (stopped whatever it is doing). The snapshot carries `resumed: {sessions: [{id, name}]}` while a session the launch resumed still runs, and leaves it out otherwise, and `where` (`inside`, `terminal` or `command`), which the Sessions page's empty state reads. The page asks `GET /api/sessions/new` only when the New session form opens: it looks through the clone folders, reading at most 4096 entries of each (Open work, Reviews and My PRs find a clone the same way, so a clone folder with more entries than that may hide a clone from all of them).

What this relies on in the Claude Code terminal renderer (header comment of `internal/ask/ask.go`; a different renderer can make a screen read as `unknown`, which fails safe, but cannot be assumed to be caught otherwise):

- Verified on real sessions: the permission dialog's footer is followed by one full-width rule, which carries the session's name in a named session (`──── name ─`); every row of a multi-line command is drawn with a ` │ ` prefix, even rows that look like rules or `Do you want to proceed?`; the frame's rules and dotted rules start at column 0 while title, description, question and options start at one space; in the transcript view a wrapped over-long command row continues indented, not at column 0.
- Assumed, not captured: the question picker's footer is followed by the same bottom rule; wrapped rows inside a permission dialog's command are also indented; a `\r` or an escape sequence in a command cannot put a rule at column 0; an Edit or Write permission draws its content inside its own frame (such a screen is `unknown` here); a digit picks a numbered option wherever the picker's cursor is (with the cursor on `Type something.` the digit may instead be typed into that field; only the numbered options are offered as buttons).
