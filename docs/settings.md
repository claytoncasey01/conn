# Settings

`#/settings` holds what conn may read. The first thing to choose is the repository allowlist: patterns like `acme/widgets` or `acme/*` (whole owner, never a partial name; `*`, `*/*` and `acme/re*` are refused; matched case-insensitively; at most 25). It limits what conn reads, not what a session's own `claude` can reach. With no `settings.json`, or one whose allowlist is missing or empty, conn is in setup: the snapshot carries `setup: true`, every page but the themes sends you to Settings, which says "Choose what conn may read. Nothing is fetched until you do.", and Settings makes no `gh` call until you press BROWSE GITHUB. The file is read once, when conn starts: a hand edit, or deleting `settings.json` to get back to setup, takes effect after you restart conn (until then, only a save from another tab moves setup), and the next save writes what conn holds in memory.

The readers (My PRs, Reviews, Sessions, History) follow the allowlist and the setup gate: My PRs ([my-prs.md](my-prs.md)) and Reviews ([reviews.md](reviews.md)) as their pages say, Sessions and History as below.

- **What conn writes for settings, and all of it:** `$CONN_DATA/settings.json`, and once, `$CONN_DATA/settings.json.bak` (a copy, made before the first save over a file conn could not read: invalid JSON, not an object, another version or too big; never overwritten, and the page says when it made one). `settings.json` is mode 0600, written to a temp file and renamed, so a failed save leaves the old file; the folder is made 0700). Nothing else is written, and a save happens only when you press a save button (`PUT /api/settings/<section>`, one section at a time, validated first: a bad entry is a 400 naming it and nothing is changed).
- **What conn calls for settings, and all of it:** `gh api user`, `gh api user/orgs` and `gh repo list <owner>`, only when you press BROWSE GITHUB (`POST /api/settings/browse`, at most 30 owners and 100 repos each). Both writes need the `x-conn: 1` header and the server's own `Origin` (a browser always sends one on a PUT or POST; a request without one is refused), like the other writes, and the secret, like every `/api` request. Everything else on the page is read from memory and from git config files on disk (never a `git` process).
- **A hand-edited file** never stops the server and never widens access: invalid JSON, a wrong type or another version is read as the defaults (setup) and the file is left as it is; a bad pattern is dropped, an `allow` that is not a list is setup; the first save over an unreadable file keeps it as `settings.json.bak`; the page lists what was dropped and the server logs it at boot.
- **Dry runs.** `CONN_MYPRS_DRY=1`, `CONN_REVIEWS_DRY=1` and `CONN_WORK_DRY=1`, alone or together, start a server whose data dir has no `settings.json` from one seed: `acme/*` allowed, and only the modules of the switches that are on: GitHub only with `CONN_MYPRS_DRY` or `CONN_REVIEWS_DRY`, `Requests me` only with `CONN_REVIEWS_DRY`, Atlassian only with `CONN_WORK_DRY` (for the project `PROJ`, with `acme/widgets` as the default repository and a second allowed repository, `acme/gadgets`, each from a stand-in clone folder whose default branch is `main`), and Slack never. In a seeded run every module (My PRs, Reviews and Open work) runs dry, whichever switches are set and whatever is turned on later from its Settings page, so nothing under the invented list reads the real GitHub, Slack or Jira: `CONN_WORK_DRY=1` alone leaves My PRs and Reviews off (no `gh`, and `reviews.json` is not read or migrated), and turning GitHub or Atlassian on there shows their dry data. The Settings page's own CHECK and BROWSE GITHUB stay real calls (`gh auth status`, `gh api user`, `gh api user/orgs`, `gh repo list`, and one connector probe run per CHECK of Slack or Atlassian), made only when you press them. The seed is written to a temp folder (`conn-dry-settings-*` in the system temp dir, holding `settings.json` and, with `CONN_WORK_DRY`, the stand-in clone `dry-clone/`) the settings are then read from, so it holds for that run only, a save from the Settings page goes there too, and nothing is written into `$CONN_DATA`. The folder is removed when the server exits or is stopped (`conn stop`, Ctrl+C); a server killed outright leaves it behind. There is no seed when a `settings.json` exists (the switches then fake only their own module, as before), with `CONN_DRY_SEED=0`, or when `CONN_DATA` is unset or is `~/.config/conn`, also through a link (stderr says so, and setup stays as it is).
- **A session's or a clone's repo** is the `github.com` `origin` in its git config on disk (https, `git@github.com:` and `ssh://git@github.com/` urls only; another host, a GitHub Enterprise host, an ssh port, and a url that only works through a `url.<base>.insteadOf` rewrite are not read, so that folder is in no repo; the nearest `.git` going up; a worktree's `.git` file is followed to its common dir), cached until the config's modification time changes. A clone for a repo is found at `repos.clones[owner/repo]`, then `<cloneRoot>/<repo>`, then `~/projects/<repo>`, and only when the folder is a repo root (`.git` directly in it, so a subfolder of a clone is not one) whose origin is that repo, with the repo name in the casing it was seen in or lowercase, and the folder reported as it is on disk; conn never clones for you.
- **Sessions and History under the allowlist.** A live session whose folder is in a repo that is not allowed is left out of Sessions and the counts (and no `gh` is run for it); one in no repo always stays, and so does a session in a folder that no longer exists (a folder is attributed to a repo only while it exists), and one conn itself started stays while it is alive: an Open work run (named after the run and in that run's recorded worktree), or a review (named so, in a worktree under `$CONN_DATA/reviews`) or a self-review (named so, in a worktree under `$CONN_DATA`). History keeps a `repo` per entry (the origin of the session's folder when it was captured) and captures nothing while conn is in setup, and no session of a repo that is not allowed; entries in no repo, or whose repo could not be known (old ones whose folder is gone), stay visible. A repo you remove from the list is hidden, never deleted: its entries, and the sessions' transcripts, stay where they are, and adding the repo back shows them again at once (and a pass over the transcripts under `~/.claude/projects` brings in the sessions the first pass skipped, with no restart). While hidden, its entries cannot be opened, summarised or resumed. The first start of this version adds a `repo` column to `history.db` (schema version 3) and fills it from the git config of each entry's folder that still exists; an older conn refuses a version 3 file, so History is off there until it is upgraded again. Settings still suggests the repos History holds, hidden ones included, so one can be added back.
- **Only `github.com` origins are attributed.** A session's repo is read from its folder's `github.com` `origin` (https, `git@github.com:` or `ssh://git@github.com/`). An ssh host alias (`git@github-work:org/repo`), a GitHub Enterprise host, an ssh port or a url rewritten by `insteadOf` is not read, so that folder is in no repo: it is always visible, and conn runs no `gh pr view` for it, so such a session shows no PR link on Sessions. Only a folder in an allowed repo is looked up on GitHub, and gh is always told that repo (`gh pr view --repo <owner/repo> -- <branch>`): it never picks one itself, so a fork whose gh default is its upstream is still asked about the fork. The branch asked about is the one on origin the session's branch tracks, as its git config says (a SELF-REVIEW worktree's `conn-self-<n>` tracks the PR's own branch), else the session's branch itself. A branch named with digits alone is not looked up (gh would read it as a PR number).
- **Backfill and summaries under the allowlist.** The import of old transcripts decides from a transcript's own first lines (the working folder they name) and does not read a transcript of a folder that exists in a repo off the list; one whose folder is gone is read, and is attributed to no repo. One import runs at a time: a list saved while it runs makes one more after it. A summary is never written for an entry in a repo off the list, even one queued before the repo was removed.
- **The repo filter.** Sessions, My PRs, Reviews and History get a `Repo` group in their filter bar whose chips are the distinct repos in that page's data (History: the repos of the entries it may show, with the server's counts, asked as `repos=owner/repo,...`); it is hidden when there is one repo or none, unless a repo is selected, so a selection can always be cleared. A session in no repo is left out once a repo is chosen.
- **Where sessions open** (`sessions.where`, default `inside`; `sessions.resumeOnLaunch`, default on). It applies to every session conn starts: an Open work build, a review, a self-review and a History resume.
  - *Inside Conn* runs `CONN_CLAUDE` on a terminal conn holds, shown on Sessions and the run page. The program must be claude itself, or a wrapper that execs claude in its place: conn links the session to claude's own registry by the process id it started, so a wrapper that starts claude as a child leaves the row "Not linked to a Claude session yet" and it cannot be replied to. A panel that closed because the program printed faster than the page could draw (`yes`, say) offers **Interrupt**, which sends Ctrl-C to the program (also on the hosted Sessions card, while the program runs). A second press within 3 seconds is not sent, since two Ctrl-C close together make claude quit: the button rests for those seconds and the server answers "already sent".
  - *My terminal* is cmux (`CONN_CMUX`), as before. No setting names a program; a `terminalCommand` an earlier build wrote is not read (the page says so, and the next save drops it).
  - *Show me the command* starts nothing and shows the line to paste: `cd <folder> && <claude and its arguments>`, each word quoted for sh, bash, zsh and fish (not csh or tcsh, which expand `!` inside quotes). A folder, name or argument holding a control character, a bidirectional control or bytes that are not UTF-8 starts nothing in any mode and gives no line: a line editor acts on such bytes before any quote is read.
  - Against the cmux sessions of earlier builds: a review or self-review now starts with "Read .conn/prompt.md and follow it exactly." (the prompt is in that file; `"$(cat …)"` cannot be passed as an argument), the program is `CONN_CLAUDE` as configured rather than the word `claude`, and `--` ends claude's options before that first message. `.conn` must be a folder of your own: a `.conn` link a repository commits is refused, and nothing is written through it.
- `settings.json` has `version`, `repos` (`allow`, `clones`, `cloneRoot`), `github`, `slack`, `atlassian`, `reviews` and `sessions`. The module and review-source switches are validated, stored and shown with their status now; My PRs (with its Slack draft), Reviews and Open work follow them (see [My PRs](my-prs.md), [Reviews](reviews.md) and [Open work](open-work.md)).
- **Services.** GitHub, Slack and Atlassian are modules: a switch, a status line with CHECK, and their own settings (Slack: channels, a DM scan switch, the channel drafts go to; Atlassian: Jira project keys, an optional default repository, a base branch for every repository without its own and an optional one per allowed repository, when the ticket moves to review, and how sessions are laid out across repositories). A module that is off makes no call and its screens are gone; its card still shows its settings, greyed, with "Off: conn makes no calls". A channel is `#` and lowercase letters, digits, dots, dashes and underscores (at most 20); a Jira key is a capital then up to nine capitals or digits (at most 20); the draft channel must be one of the channels; the default repository (`buildRepo`) is optional (the repository Open work's start panel ticks when the browser has no earlier choice; Open work does not need one, because repositories are chosen per ticket at START), must be an allowed repo (never `owner/*`) and is cleared when it leaves the list. In `atlassian.jira`, `baseBranch` is the base branch for every repository without its own, `baseBranches` maps a lowercase `owner/repo` to its own base branch (a save replaces the whole map, and entries for repositories that leave the allowlist are dropped), `reviewMove` is `first`, `all` (the default) or `never` (move the ticket to review after the first PR, after every repository with changes has one, or never) and `sessionLayout` is `shared` (the default: one session across a run's repositories) or `split` (one session per repository), the layout the start panel begins on. Each repository's base branch is its `baseBranches` entry, else `baseBranch`, else the clone's default branch (see [Open work](open-work.md)). A save that leaves one of these keys out keeps it, and a body with bad values is refused with every problem named at once. Each card saves on its own button, one section per `PUT /api/settings/<section>`, nothing on a timer or on input.
- **What each switch stops, and what each module calls.**
  - GitHub (`gh`, signed in): off stops My PRs (its `gh` search, its thread replies and resolves), Reviews and the PR links on sessions. History and Sessions stay. CHECK runs `gh auth status`, once.
  - Slack (your claude.ai Slack connector, through short metered `claude -p` runs with only the Slack read tools): off stops the channel scan, the DM scan and the My PRs ready-for-review Slack draft (a draft in your Slack, never sent); Reviews then lists from GitHub alone. CHECK runs one `claude -p` run (the cheapest model, capped at $0.25 and 60 s) that calls `slack_read_user_profile` once.
  - Atlassian (your claude.ai Atlassian connector, same kind of run): off stops Open work (nav item, route and API), ticket sessions and the PR OR TICKET filter, and ticket links. CHECK runs one such run that calls `atlassianUserInfo` once.
- **Status is never fetched on its own.** `GET /api/settings` only reads what conn holds in memory: GitHub and the connectors show "Not checked yet" until a run records how it went (each My PRs and Reviews poll, a Reviews scan of Slack channels or DMs, a My PRs Slack draft, Open work's sprint read, Jira moves and research readers: one fixed line of conn's own, never text from GitHub or Slack) or you press CHECK (`POST /api/settings/check/<github|slack|atlassian>`: one probe of that module, run when you press and never on a timer or when the page loads; a module whose switch is saved off is refused with a 409 and nothing runs; two presses at once share one run). A probe shows only a login, the user's display name, a fixed sentence or one short error line, cleaned and cut (token-shaped words removed), never raw output. A module that is on and failing shows its error on its card.
- **Review sources.** "Which PRs Reviews lists" has the two switches (`reviews.requested`, default on, and `reviews.allOpen`, default off), the two derived sources (a channel scan needs Slack on and at least one channel; the DM scan needs Slack on and its switch), and one sentence that says what the combination lists, as edited, before it is saved. With only "Requests me" and no Slack read, Reviews makes no Slack call.
- **What conn calls for modules, and all of it:** `gh auth status` and, per connector, one `claude -p` probe run, each only when you press CHECK; both need the `x-conn: 1` header and a local `Origin`, like the other writes. Nothing else is added here: saving a card is the same `PUT` as above.

## Agents and skills

Conn carries a few agents (`agents/`) and skills (`skills/`) for Claude Code in its binary. At every start it copies them into `$CONN_DATA/agents/` and `$CONN_DATA/skills/` (a copy that is the same is not rewritten; a different one is replaced, and a skill's folder is made whole beside the old one and swapped in, so edits to a copy are lost). It links nothing else without being asked:

- **Agents** are linked at start: `~/.claude/agents/<name>.md` becomes a symlink to the copy. This happens only when the data folder is the default one (`~/.config/conn`, or `$XDG_CONFIG_HOME/conn`) and not in a dry run, so a `make dev` server, whose data folder is `~/.config/conn-dev`, never points your Claude folder at its scratch copies. A link that is missing comes back at the next start.
- **Skills** are linked only when you press INSTALL on the Settings page (Agents and skills): `~/.claude/skills/<name>` becomes a symlink to the copy. Conn ships `deep-code-review`, the in-depth review that Reviews and the My PRs Self-Review prompts use when it is installed: it ranks findings P0 to P3, and when the prompt asks it to post, it comments inline and approves when no P0 or P1 survives (as a comment on your own PR, which GitHub will not let you approve). REMOVE takes that link away and nothing else. Nothing is installed by default.
- **Nothing of yours is replaced.** If a file, a folder or a link to somewhere else is already at the place, conn leaves it and the page says it is in the way (the log says so for an agent). Only a link that points at conn's own copy is conn's: it is the only kind REMOVE removes, and the only kind removed at start when conn no longer provides that agent or skill.
- **Files written:** the copies under `$CONN_DATA`, the symlinks, and the `~/.claude/agents` or `~/.claude/skills` folder when it does not exist yet. A script in a skill keeps its executable bit only if it starts with `#!`.

The routes: `GET /api/provided` (the state of every agent and skill, read from the disk), and `POST /api/provided/install` and `/remove` with `{"name": "<skill>"}`, behind the same POST and `x-conn` guard as the other writes. Only skills can be installed or removed this way.
